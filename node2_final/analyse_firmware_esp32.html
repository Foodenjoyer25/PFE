// lib_deps = me-no-dev/AsyncTCP, me-no-dev/ESPAsyncWebServer
//

//   -DCONFIG_ASYNC_TCP_RUNNING_CORE=0

//   -DCONFIG_ASYNC_TCP_QUEUE_SIZE=64
//   -DCONFIG_ASYNC_TCP_STACK_SIZE=8192

#include <WiFi.h>
#include <time.h>
#include <AsyncTCP.h>

#include <Preferences.h>
#include <map>
#include <vector>
#include <atomic>

L'en-tête du fichier remplit deux fonctions documentaires distinctes. Les commentaires liminaires rappellent les dépendances externes (les bibliothèques AsyncTCP et ESPAsyncWebServer de me-no-dev) ainsi que les macros de compilation indispensables au comportement attendu. Cette duplication entre fichier source et platformio.ini est volontaire : un développeur ouvrant le seul .cpp comprend immédiatement les prérequis sans avoir à inspecter la configuration de build.

Les inclusions, ensuite, dévoilent l'ambition du projet. On y trouve les en-têtes attendus pour un projet Arduino-ESP32 connecté — WiFi.h, time.h, AsyncTCP.h, ESPAsyncWebServer.h — mais aussi un bouquet d'en-têtes de la bibliothèque standard C++ qui trahit un style d'écriture résolument moderne : <map> pour la table des IP, <vector> pour l'historique, <atomic> pour la communication inter-cœurs sans verrou, et <freertos/semphr.h> pour les mutex FreeRTOS. La cohabitation de la STL et des primitives FreeRTOS est l'un des marqueurs de ce code : il refuse l'opposition entre confort moderne et contrôle bas-niveau.

À retenir Le choix de std::atomic et de SemaphoreHandle_t côte à côte annonce déjà la stratégie de concurrence : lock-free pour les scalaires partagés, mutex pour les conteneurs complexes.

Configuration réseau et bus capteur

// ── Configuration réseau ──────────────────────────────────────────
const char* SSID     = "BaslimaneR";
const char* PASSWORD = "ishak2012";

#define UART_RX_PIN  16
#define UART_BAUD    115200

Quatre paramètres définissent le lien physique du nœud avec le reste du monde. Les identifiants WiFi sont codés en dur — pratique courante en prototypage, mais à proscrire en production : un firmware extrait par lecture de la flash exposerait immédiatement le mot de passe du réseau. Une version durcie utiliserait WiFiManager pour saisir les identifiants au premier démarrage et les stocker, chiffrés, dans la NVS.

Côté capteur, la broche 16 de l'ESP32-S3 est configurée comme entrée UART (RX), à 115 200 bauds — choix identique à celui de la console série, ce qui simplifie le débogage. Aucune broche TX n'est définie pour Serial2 (voir bloc 18 : Serial2.begin(UART_BAUD, SERIAL_8N1, UART_RX_PIN, -1)), confirmant la nature unidirectionnelle du flux : le capteur émet, le nœud écoute.

Paramètres de détection DDoS

#define DDOS_WINDOW_MS       1000   // Durée de la fenêtre de comptage (ms)
#define DDOS_PPS_THRESHOLD   10     // Seuil de requêtes/s par IP avant bannissement
#define DDOS_GLOBAL_PPS_MAX  200    // Seuil global d'alerte trafic élevé
#define DDOS_TABLE_LIMIT     200    // Nombre maximum d'IP dans la table
#define CLEANUP_INTERVAL_MS  30000  // Intervalle de nettoyage de la table IP
#define BAN_LOG_THROTTLE_MS  1000   // Anti-spam des messages de bannissement
#define HEAP_LOG_INTERVAL_MS 10000  // Intervalle d'affichage de la mémoire libre

Ce bloc concentre les seuils opérationnels du moteur de détection. Chaque valeur encode une décision d'ingénierie qu'il importe d'expliciter.

Le seuil de 10 requêtes par seconde et par IP est calibré pour un usage domestique : un navigateur normal effectue au plus une poignée de requêtes lors d'un chargement de page, et l'interface web utilisant SSE après cela ne génère plus aucun appel HTTP entrant. Dix requêtes par seconde révèlent donc presque certainement un script automatisé.

Le seuil global de 200 PPS ne déclenche pas de bannissement individuel mais lève une alerte journalisée : il permet de distinguer une attaque ciblée (une IP au-dessus du seuil personnel) d'une attaque distribuée où chaque IP reste légalement sous le seuil mais où la somme dépasse la capacité de traitement.

La limite de 200 IP simultanées dans la table protège la mémoire : un attaquant ne peut pas saturer le tas en simulant un grand nombre d'adresses sources. C'est une borne dure qui transforme la table en structure à capacité constante, propriété précieuse sur un microcontrôleur.

Notez la transition stylistique entre les deux groupes : les valeurs de politique de sécurité restent en #define (héritage C, conforme à l'esthétique Arduino), tandis que les constantes opérationnelles migrent vers static constexpr, plus moderne et typée. Cette dichotomie n'est pas anodine : elle place explicitement les paramètres de sécurité dans un registre lexical différent.

Le poids de chaque constante

NET_TASK_STACK = 6144 octets : la tâche réseau manipule des chaînes JSON pouvant atteindre plusieurs kilo-octets (l'historique sérialisé représente jusqu'à 100 entrées) ; cette réservation est confortable mais non excessive sur un ESP32-S3 doté de 320 Ko de SRAM. NET_TASK_PRIO = 5 : priorité supérieure à celle de la tâche AsyncTCP (fixée à 3 dans le platformio.ini), ce qui garantit la primauté de la logique de contrôle sur le traitement brut des paquets — décisif pendant une attaque. NET_TASK_CORE = 0 : exécution sur le PRO_CPU, là où tourne déjà la pile TCP, pour exploiter une affinité de cache.

La classe TcpGateWebServer

class TcpGateWebServer : public AsyncWebServer {
public:
    using GateFn = bool (*)(const String& ip);

    explicit TcpGateWebServer(uint16_t port) : AsyncWebServer(port) {}

    void setGate(GateFn fn) { _gate = fn; }

    void begin() {
        _server.onClient([](void* s, AsyncClient* c) {
            auto* self = static_cast<TcpGateWebServer*>(s);
            if (!c) return;

            // Fermer immédiatement les connexions bannies au niveau TCP
            if (self->_gate && self->_gate(c->remoteIP().toString())) {
                c->onDisconnect([](void*, AsyncClient* client) {
                    delete client;
                }, nullptr);
                c->close(true);
                return;
            }

            c->setRxTimeout(3);
            AsyncWebServerRequest* r = new AsyncWebServerRequest(self, c);
            if (r == nullptr) {
                c->onDisconnect(...);
                c->close(true);
            }
        }, this);

        AsyncWebServer::begin();
    }
private:
    GateFn _gate = nullptr;
};

Ce bloc est la pierre angulaire de la défense en profondeur. La classe étend AsyncWebServer en interceptant le callback onClient du serveur TCP sous-jacent — un point d'extension peu documenté mais offert par la bibliothèque AsyncTCP.

L'idée est radicale : filtrer les connexions au niveau TCP, avant même que l'objet AsyncWebServerRequest ne soit alloué. Lorsqu'une IP figure sur la liste de bannissement, la connexion est fermée par c->close(true), et un callback de libération mémoire est attaché à la déconnexion pour delete client — sans cela, l'objet AsyncClient resterait en fuite. Aucune allocation HTTP, aucune analyse de méthode ni d'URL : l'attaquant ne consomme que le coût d'un paquet SYN/FIN.

Le setRxTimeout(3) appliqué aux connexions légitimes constitue une protection complémentaire contre les attaques de type Slowloris, où l'attaquant maintient des connexions à demi ouvertes sans jamais compléter sa requête HTTP. Trois secondes pour achever l'envoi d'en-têtes HTTP est plus qu'amplement suffisant en réseau local.

Élégance Le typedef using GateFn = bool (*)(const String& ip) permet d'injecter dynamiquement la fonction de garde. La classe TcpGateWebServer reste ainsi découplée de la logique de détection : on pourrait substituer une autre politique sans modifier la classe.

Variables d'état globales

TcpGateWebServer server(80);
AsyncEventSource events("/events");

std::atomic<float> currentLux{0.0f};
std::atomic<bool>  luxUpdated{false};

    uint32_t      pps;
    unsigned long windowStart;
    unsigned long bannedUntil;
};

std::map<String, IpState> ipTable;
static SemaphoreHandle_t  tableMutex = nullptr;

struct LuxEntry { float value; uint32_t secs; bool prevBoot; };
static std::vector<LuxEntry> luxHistory;

std::atomic<unsigned long> lastWifiOkMs{0};

Ce bloc déclare l'état global du système. Les variables s'organisent en cinq catégories distinctes : objets serveur, valeur instantanée du capteur, table des IP, historique, et indicateurs de watchdog.

La règle de discipline mémoire

Une règle implicite guide les choix de synchronisation : les scalaires partagés entre cœurs sont std::atomic (currentLux, luxUpdated, globalPeakPps, attackStartMs, lastWifiOkMs), tandis que les conteneurs (ipTable, luxHistory) sont protégés par des mutex FreeRTOS. Cette discipline reflète une compréhension précise du modèle mémoire C++11 : une opération atomique sur un entier 32 bits est réellement non bloquante sur ESP32, alors qu'une mutation de std::map implique plusieurs allocations et rebalancements d'arbre rouge-noir qui ne peuvent en aucun cas être rendus atomiques.

La structure IpState

Trois champs suffisent à caractériser le comportement d'une IP : son compteur de paquets dans la fenêtre courante (pps), l'instant de début de cette fenêtre (windowStart), et l'instant jusqu'auquel l'IP est bannie (bannedUntil). Une valeur de bannedUntil = 0 signifie « jamais banni », une valeur = ULONG_MAX signifie « banni pour toute la session ». Cette encoding compact évite un booléen supplémentaire.

Persistance NVS de l'historique

static Preferences nvs;
#define NVS_HIST_NAMESPACE  "lhist"

static void saveLuxHistory() {
    xSemaphoreTake(historyMutex, portMAX_DELAY);
    nvs.begin(NVS_HIST_NAMESPACE, false);
    nvs.clear();
    uint16_t total = (uint16_t)luxHistory.size();
    uint16_t start = total > LUX_HISTORY_MAX ? total - LUX_HISTORY_MAX : 0;
    uint16_t saved = 0;
    for (uint16_t i = start; i < total; ++i) {
        char vk[8], tk[8];
        snprintf(vk, sizeof(vk), "v%u", saved);
        snprintf(tk, sizeof(tk), "t%u", saved);
        nvs.putFloat(vk, luxHistory[i].value);
        nvs.putULong(tk, luxHistory[i].secs);
        ++saved;
    }
    nvs.putUShort("n", saved);
    nvs.end();
    xSemaphoreGive(historyMutex);
}

static void loadLuxHistory() { /* symétrique, prevBoot = true */ }

La paire saveLuxHistory / loadLuxHistory assure la continuité temporelle de l'historique au travers des redémarrages, qu'ils soient normaux, accidentels ou provoqués par un watchdog.

L'implémentation s'appuie sur la bibliothèque Preferences d'Arduino-ESP32, elle-même surcouche du système NVS d'ESP-IDF. Le NVS gère automatiquement la répartition d'usure (wear leveling) sur la flash et inclut une somme de contrôle qui détecte la corruption. Chaque entrée est sérialisée sous deux clés : v<i> pour la valeur flottante, t<i> pour le timestamp Unix. Une clé supplémentaire n stocke le nombre d'entrées, permettant à loadLuxHistory de connaître la borne supérieure de la boucle de lecture.

Le drapeau prevBoot

Lors de la restauration, chaque entrée est marquée prevBoot = true. Cette information est ensuite propagée au navigateur dans le JSON sérialisé (champ "p"), ce qui permet à l'interface web de tracer une ligne de séparation visuelle « — previous boot — » entre les mesures héritées et celles de la session courante. C'est un geste d'honnêteté du système envers son utilisateur : le redémarrage n'est pas dissimulé comme un incident, il est révélé comme une information.

Considération matérielle À 5 760 écritures par jour (une toutes les 15 secondes), même avec une endurance flash conservative de 100 000 cycles par secteur et la répartition d'usure du NVS, la durée de vie utile dépasse plusieurs années — largement compatible avec un déploiement domestique.

Le watchdog d'attaque

static void markAttackActivity(unsigned long now) {
    unsigned long expected = 0;
    attackStartMs.compare_exchange_strong(expected, now,
        std::memory_order_relaxed, std::memory_order_relaxed);
}

static void runAttackWatchdog(unsigned long now) {
    unsigned long start = attackStartMs.load(std::memory_order_relaxed);
    if (start == 0) return;

    if (now - start >= ATTACK_REBOOT_MS) {
        Serial.printf("[!!!] Attaque détectée depuis %lu ms — sauvegarde et redémarrage\n", now - start);
        Serial.flush();
        saveLuxHistory();
        delay(100);
        ESP.restart();
    }
}

Voici sans doute le passage le plus subtil du firmware. Le watchdog d'attaque repose sur un mécanisme atomique en deux temps qui mérite une analyse fine.

markAttackActivity est appelée à chaque blocage d'IP. Mais au lieu d'écraser naïvement attackStartMs avec l'instant courant, elle utilise compare_exchange_strong(expected=0, now). La sémantique est limpide : la valeur n'est mise à jour que si elle vaut encore 0. Toute détection ultérieure trouvera attackStartMs ≠ 0 et l'opération échouera silencieusement, laissant le timestamp initial intact.

Pourquoi cette précaution ? Sans elle, chaque nouvelle détection réinitialiserait le compteur, et un attaquant maintenant un flux continu de paquets juste au seuil de détection empêcherait indéfiniment l'expiration du délai de 30 secondes. Le code rend cette manipulation impossible : 30 secondes après la première détection, le redémarrage est inéluctable, quelle que soit la cadence d'attaque qui suit.

Avant ESP.restart(), le code Serial.flush() assure que les messages de diagnostic atteignent bien la console, saveLuxHistory() persiste l'état, et un delay(100) laisse aux opérations matérielles le temps de se terminer. Ces trois précautions transforment ce qui pourrait être un crash brutal en une terminaison gracieuse.

Le redémarrage n'est plus un échec ; c'est une stratégie. Le firmware embrasse le modèle crash-only popularisé par Candea et Fox : la seule récupération fiable est la réinitialisation propre.

Anti-spam des logs et application du bannissement

static bool shouldLog(uint32_t nowMs) {
    uint32_t last = lastLogMs.load(std::memory_order_relaxed);
    if (nowMs - last < BAN_LOG_THROTTLE_MS) return false;
    return lastLogMs.compare_exchange_strong(
        last, nowMs, std::memory_order_relaxed, std::memory_order_relaxed);
}

static inline void applyBan(IpState& s) {
    s.bannedUntil = ULONG_MAX;
    s.pps         = 0;
}

Deux fonctions utilitaires, deux préoccupations très différentes.

shouldLog résout un problème classique en sécurité : les logs eux-mêmes peuvent devenir une vulnérabilité. Lors d'une attaque à 1 000 paquets par seconde, inonder la console série de messages « BANNI x.x.x.x » saturerait le tampon UART, ralentirait drastiquement le cœur qui produit ces logs, et pourrait noyer des messages importants. La fonction n'autorise un log que toutes les BAN_LOG_THROTTLE_MS = 1000 millisecondes. Le compare_exchange_strong garantit que même si plusieurs tâches appellent shouldLog simultanément, une seule réussira à imprimer ce tick — propriété indispensable dans un contexte multi-cœur.

applyBan est minimaliste mais son commentaire en dit long : « L'appelant doit détenir tableMutex ». Cette convention de précondition non vérifiée est un classique des codes embarqués : la vérification ajouterait un coût alors que le contrat est respecté par toutes les routines appelantes. La marque inline élimine tout coût d'appel, transformant la fonction en pure annotation sémantique.

Le moteur checkAndRate

bool checkAndRate(const String& ip) {
    const unsigned long now = millis();
    xSemaphoreTake(tableMutex, portMAX_DELAY);

    auto it = ipTable.find(ip);
    if (it != ipTable.end()) {
        if (it->second.bannedUntil && it->second.bannedUntil > now) {
            xSemaphoreGive(tableMutex);
            markAttackActivity(now);
            return false;
        }
    } else if (ipTable.size() >= DDOS_TABLE_LIMIT) {
        xSemaphoreGive(tableMutex);
        markAttackActivity(now);
        return false;
    }

    // Fenêtre globale : reset toutes les 1000 ms, capture du pic
    if (now - globalWinStart >= DDOS_WINDOW_MS) {
        if (globalPps > globalPeakPps.load(...))
            globalPeakPps.store(globalPps, ...);
        globalPps = 0;
        globalWinStart = now;
    }
    ++globalPps;

    // Fenêtre par IP : reset glissant, incrément, test du seuil
    IpState& s = (it != ipTable.end()) ? it->second : ipTable[ip];
    if (now - s.windowStart >= DDOS_WINDOW_MS) {
        s.windowStart = now;
        s.pps         = 0;
    }
    ++s.pps;

    bool banned = (s.pps > DDOS_PPS_THRESHOLD);
    if (banned) applyBan(s);

    xSemaphoreGive(tableMutex);

    if (banned) {
        markAttackActivity(now);
        return false;
    }
    return true;
}

Le cœur analytique du système. Cette fonction est appelée pour chaque requête HTTP entrante et décide en une seule passe : laisser passer ou bloquer.

Trois portes en cascade

La fonction présente une structure en trois portes successives. Première porte : si l'IP est déjà bannie, refus immédiat. Deuxième porte : si la table est pleine et l'IP inconnue, refus par protection mémoire. Troisième porte : comptage et test du seuil. Cet ordre n'est pas indifférent : les cas les plus fréquents en situation d'attaque (IP déjà bannies) sont traités les premiers, économisant le travail en aval.

Une nuance d'optimisation

La ligne IpState& s = (it != ipTable.end()) ? it->second : ipTable[ip] est élégante : si l'IP existait déjà, on réutilise l'itérateur déjà calculé ; sinon, ipTable[ip] insère une nouvelle entrée (constructeur par défaut). Cela évite une seconde recherche dans l'arbre rouge-noir, opération coûteuse en log(n).

L'effet du double appel à markAttackActivity

Cette fonction est invoquée à trois endroits distincts : refus pour bannissement, refus pour table pleine, et nouveau bannissement. Or, grâce au mécanisme compare-exchange du bloc 08, ces multiples appels n'enregistrent qu'un seul instant de début d'attaque — le premier. La cohérence du système émerge de la combinaison de fonctions simples, chacune respectant sa propre invariance.

Le filtre gateShouldBlock

bool gateShouldBlock(const String& ip) {
    const unsigned long now = millis();
    xSemaphoreTake(tableMutex, portMAX_DELAY);

    auto it = ipTable.find(ip);
    if (it == ipTable.end()) {
        xSemaphoreGive(tableMutex);
        return false;
    }
    if (it->second.bannedUntil && it->second.bannedUntil > now) {
        xSemaphoreGive(tableMutex);
        markAttackActivity(now);
        return true;
    }
    xSemaphoreGive(tableMutex);
    return false;
}

Cette fonction est la contrepartie en lecture seule de checkAndRate. Elle ne modifie pas l'état, n'incrémente aucun compteur — elle se contente de répondre à une seule question : cette IP est-elle bannie en ce moment ?

Elle est invoquée par deux clients très différents : le filtre TCP du bloc 05 (qui doit décider s'il ferme la connexion sans même la traiter) et le middleware HTTP du bloc 14 (qui doit décider s'il intercepte la requête). Cette séparation entre lecture et écriture est une bonne hygiène de conception : gateShouldBlock est très rapide car elle évite toute la mécanique de comptage, ce qui réduit le temps passé sous mutex.

Nettoyage cleanupIpTable

void cleanupIpTable() {
    const unsigned long now = millis();
    xSemaphoreTake(tableMutex, portMAX_DELAY);
    for (auto it = ipTable.begin(); it != ipTable.end(); ) {
        bool banned = (it->second.bannedUntil > now);
        bool idle   = (now - it->second.windowStart > 30000);
        it = (!banned && idle) ? ipTable.erase(it) : std::next(it);
    }
    size_t sz = ipTable.size();
    xSemaphoreGive(tableMutex);
    Serial.printf("[DDoS] Table: %u entrées | pic: %u PPS | heap: %u\n", ...);
}

Sans entretien, la table grandirait à chaque nouvelle IP rencontrée jusqu'à atteindre la limite de 200. Cette fonction, appelée toutes les 30 secondes par netTask, supprime les entrées qui sont à la fois non bannies et inactives depuis plus de 30 secondes.

Le critère composé est significatif : un client légitime qui visite la page puis se déconnecte libère son entrée après 30 secondes ; un bannissement, en revanche, reste éternel — c'est le comportement attendu d'une liste de réputation. L'idiome it = (...) ? erase(it) : std::next(it) est l'écriture canonique de la suppression sûre pendant l'itération sur une collection STL.

Le log final agrège trois métriques opérationnelles en une seule ligne : taille de la table, pic global de PPS depuis le dernier nettoyage, et mémoire libre. C'est l'équivalent d'un tableau de bord miniature, utile pour le diagnostic à long terme.

Reconnexion ensureWifi

bool ensureWifi() {
    static unsigned long lastTryMs = 0;
    const unsigned long now = millis();

    if (WiFi.status() == WL_CONNECTED) {
        lastWifiOkMs.store(now, std::memory_order_relaxed);
        return true;
    }

    // Redémarrage d'urgence si WiFi perdu trop longtemps
    unsigned long lastOk = lastWifiOkMs.load(std::memory_order_relaxed);
    if (lastOk > 0 && now - lastOk > WIFI_DEAD_REBOOT_MS) {
        Serial.printf("[!!!] WiFi perdu depuis %lu ms — sauvegarde et redémarrage\n", now - lastOk);
        Serial.flush();
        saveLuxHistory();
        delay(100);
        ESP.restart();
    }

    if (now - lastTryMs < WIFI_RETRY_MS) return false;
    lastTryMs = now;

    Serial.println("[WiFi] Déconnecté, reconnexion…");
    WiFi.disconnect();
    WiFi.begin(SSID, PASSWORD);
    return false;
}

Cette fonction traite un cas spécifique mais redoutable de l'ESP32 : sous une inondation suffisamment violente, le pilote WiFi peut entrer dans un état corrompu d'où aucune séquence de reconnexion logicielle ne le sort. Le commentaire du code l'admet sans détour : « un redémarrage propre est le seul remède fiable ».

La logique procède en trois étages. Premier étage : si la connexion est établie, mettre à jour lastWifiOkMs — c'est le tic-tac vital du watchdog WiFi. Deuxième étage : si la déconnexion persiste depuis plus de WIFI_DEAD_REBOOT_MS = 120 000 millisecondes (2 minutes), déclencher la procédure d'urgence : flush, save, restart. Troisième étage : sinon, espacer les tentatives de reconnexion de 5 secondes pour ne pas matraquer la pile WiFi avec des appels inutiles.

Subtilité Le test lastOk > 0 évite un redémarrage immédiat au tout premier appel, où lastWifiOkMs vaut encore 0. Sans ce garde-fou, le système redémarrerait en boucle si la connexion initiale échouait.

Le middleware RateLimitMiddleware

class RateLimitMiddleware : public AsyncWebHandler {
public:
    bool canHandle(AsyncWebServerRequest* req) const override {
        AsyncClient* c = req->client();
        if (!c) return false;
        const String ip = c->remoteIP().toString();
        if (gateShouldBlock(ip)) return true;
        return !checkAndRate(ip);
    }

    void handleRequest(AsyncWebServerRequest* req) override {
        AsyncWebServerResponse* resp = req->beginResponse(429, "text/plain", "Too Many Requests");
        resp->addHeader("Connection", "close");
        req->send(resp);
    }
};

Ce middleware exploite une particularité d'ESPAsyncWebServer : la méthode canHandle est invoquée pour chaque requête, dans l'ordre d'enregistrement des gestionnaires. Si elle retourne true, le gestionnaire prend la main avant les handlers de route ; sinon, l'examen continue.

L'inversion sémantique est ingénieuse : canHandle retourne true précisément quand la requête est malveillante, prenant ainsi le contrôle pour répondre 429 Too Many Requests et fermer la connexion. Les requêtes légitimes, pour lesquelles checkAndRate retourne true, ne déclenchent pas canHandle et poursuivent leur chemin vers les routes normales.

L'en-tête Connection: close est essentiel : il force l'attaquant à rétablir un handshake TCP complet pour chaque tentative. Cela démultiplie son coût et accélère la saturation de la fenêtre de détection.

La tâche réseau (netTask)

void netTask(void* arg) {
    (void)arg;
    unsigned long lastHeapMs     = millis();
    unsigned long lastWatchdogMs = millis();
    unsigned long lastHistoryMs  = millis();
    unsigned long lastBannedMs   = millis();

    for (;;) {
        unsigned long now = millis();

        if (!ensureWifi()) { vTaskDelay(pdMS_TO_TICKS(50)); continue; }

        if (now - lastCleanupMs >= CLEANUP_INTERVAL_MS) {
            lastCleanupMs = now; cleanupIpTable();
        }
        if (now - lastWatchdogMs >= WATCHDOG_CHECK_MS) {
            lastWatchdogMs = now; runAttackWatchdog(now);
        }
        if (now - lastHeapMs >= HEAP_LOG_INTERVAL_MS) {
            lastHeapMs = now;
            Serial.printf("[mem] heap libre=%u min=%u\n", ...);
        }

        // Diffusion temps réel de la nouvelle valeur
        if (luxUpdated.exchange(false, std::memory_order_acquire)) {
            float lux = currentLux.load(std::memory_order_relaxed);
            events.send(String(lux, 2).c_str(), "lux", millis());
        }

        // Échantillonnage historique toutes les 15 s + sauvegarde NVS
        if (now - lastHistoryMs >= LUX_HISTORY_INTERVAL_MS) { ... }

        // Liste des IP bannies toutes les 5 s
        if (now - lastBannedMs >= BANNED_SEND_MS) { ... }

        vTaskDelay(pdMS_TO_TICKS(NET_TASK_DELAY_MS));
    }
}

netTask orchestre tout ce qui n'est pas l'acquisition de la mesure : surveillance WiFi, watchdog d'attaque, nettoyage périodique, journalisation mémoire, diffusion SSE temps réel, sauvegarde de l'historique. L'architecture est celle d'une boucle coopérative à minuteurs : une seule boucle for(;;) compare l'horloge courante à des timestamps mémorisés pour décider quelle action déclencher.

Synchronisation producteur-consommateur

La séquence if (luxUpdated.exchange(false, std::memory_order_acquire)) illustre une mécanique de synchronisation release-acquire classique. La boucle principale (cœur 1) publie une nouvelle valeur avec memory_order_release ; netTask (cœur 0) la récupère en effaçant le drapeau de manière atomique avec memory_order_acquire. Cette construction garantit que la lecture de currentLux sera bien synchronisée avec l'écriture du cœur producteur, sans qu'aucun mutex ne soit jamais pris.

Le délai de boucle

vTaskDelay(pdMS_TO_TICKS(NET_TASK_DELAY_MS)) avec NET_TASK_DELAY_MS = 2 yield le processeur toutes les 2 ms, ce qui laisse aux tâches de plus basse priorité (notamment AsyncTCP à priorité 3) l'occasion de s'exécuter. Sans ce délai, netTask à priorité 5 monopoliserait le cœur 0 et asphyxierait la pile TCP.

La fonction setup orchestre l'amorçage du système selon une séquence rigoureuse qu'on peut décomposer en huit étapes ordonnées par dépendance.

(1) Initialisation des deux ports série : la console à 115 200 bauds, et Serial2 en réception seule sur la broche 16. (2) Journalisation immédiate du motif de redémarrage via esp_reset_reason() — précieux pour distinguer un crash d'un redémarrage volontaire par le watchdog d'attaque. (3) Création des mutex, avec gestion d'échec fatale (while(true) delay()) : sans mutex, aucune cohérence multi-tâche n'est possible, mieux vaut figer le système plutôt que de poursuivre sur un état brisé. (4) Restauration de l'historique depuis NVS, ce qui doit se produire avant toute activité de la tâche réseau qui pourrait sérialiser cet historique vers les clients SSE.

(5) Connexion WiFi : setSleep(false) désactive le mode d'économie d'énergie, indispensable pour la réactivité réseau ; setAutoReconnect(true) active la reconnexion automatique du driver — ceinture en plus de ensureWifi. (6) Synchronisation NTP avec deux serveurs en redondance. (7) Configuration du serveur : injection de la garde, ajout du middleware en premier (pour qu'il s'exécute avant les routes), enregistrement de la route racine, de la route 404 et de la source d'événements. L'ordre d'enregistrement est crucial : AsyncWebServer évalue les handlers dans cet ordre, donc le middleware doit précéder les routes légitimes. (8) Lancement de netTask sur le cœur 0 avec priorité 5.

Détail révélateur Le callback events.onConnect envoie immédiatement l'historique et la liste des bannissements à chaque nouvelle connexion SSE. Un nouveau visiteur n'attend pas le prochain cycle de 15 secondes pour voir ses données — l'expérience initiale est instantanée.

Boucle principale (loop)

void loop() {
    while (Serial2.available()) {
        String line = Serial2.readStringUntil('\n');
        line.trim();
        if (line.startsWith("LUX:")) {
            float lux = line.substring(4).toFloat();
            currentLux.store(lux, std::memory_order_relaxed);
            luxUpdated.store(true, std::memory_order_release);
            Serial.printf("[UART] lux=%.2f\n", lux);
        }
    }
    delay(APP_LOOP_DELAY_MS);
}

Trompeuse de simplicité, cette fonction concentre la philosophie du firmware sur une vingtaine de lignes. Exécutée sur le cœur 1 (APP_CPU), elle n'a qu'une responsabilité : extraire les trames LUX:<valeur> du port série et les publier dans les variables atomiques partagées.

Le protocole de trame

Le préfixe "LUX:" agit comme un mot-clé d'identification : toute ligne ne le portant pas est silencieusement ignorée. Cette tolérance permet d'envoyer sur le même UART des messages de debug du capteur (par exemple « Sensor OK ») sans risquer de les voir interprétés comme des valeurs erronées. Le parsing par line.substring(4).toFloat() convertit toute chaîne malformée en 0.0f, ce qui constitue un fallback acceptable mais qu'on pourrait améliorer en exigeant un format strict (par exemple via strtof avec vérification du pointeur de fin).

La sémantique mémoire des deux store

L'ordre des deux écritures est fondamental. currentLux.store(lux, relaxed) publie la valeur sans aucune garantie d'ordre, puis luxUpdated.store(true, release) publie le drapeau avec une barrière de type release. La spécification C++ garantit alors qu'un lecteur acquérant le drapeau (le exchange du bloc 17) verra nécessairement la nouvelle valeur de currentLux. C'est l'idiome canonique du producteur-consommateur sans verrou, dont la correction repose entièrement sur cette discipline des ordres mémoire.

Le delay(APP_LOOP_DELAY_MS) en queue de fonction (5 millisecondes) yield le processeur, laissant aux tâches de plus basse priorité du cœur 1 (et au cœur 0) l'occasion d'exécuter leur travail. Sans ce délai, la boucle Arduino consommerait 100% du cœur 1 même en l'absence de données.

Synthèse

En 686 lignes, le firmware compose une partition à plusieurs voix : un cœur d'acquisition simple comme une berceuse, une tâche réseau qui tisse ses sous-mélodies temporelles, et un orchestre de défense — TCP, HTTP, comptage, watchdog — qui veille à ce que rien ne vienne troubler la mesure. Chaque bloc analysé répond à une question d'ingénierie précise, et leur articulation forme un système dont la cohérence est plus grande que la somme de ses parties.

Si l'on ne devait retenir qu'une leçon, ce serait celle-ci : la robustesse ne naît pas d'un mécanisme unique mais de leur empilement discipliné. Filtre TCP, middleware HTTP, moteur de comptage, watchdog d'attaque, watchdog WiFi, persistance NVS, redémarrage gracieux — chaque couche prend en charge un type de défaillance et délègue les autres à ses voisines. C'est précisément ce que désigne la formule defense in depth, et c'est ce qui distingue un firmware d'apprentissage d'un firmware prêt pour le terrain.
